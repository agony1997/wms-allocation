配貨單規格書 (AO)
===
> 主要操作者：庫務
---

## 概述

庫務根據業務員訂貨明細 (SPOD) 進行配貨，從大庫庫存中分配產品給各業務員。
批次一律依 FEFO（近效期先出）分配；業務員優先等級決定**分配順序**（缺貨時的數量保障，不影響批次品質）。

---

## 作業流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│  階段 1: 收貨入庫                                                        │
│  ─────────────                                                          │
│  - FDO 確認收貨                                                          │
│  - 貨品入大庫（含批次、效期）                                             │
└─────────────────────────────────────────────────────────────────────────┘
        │
        ▼ 庫務執行配貨
┌─────────────────────────────────────────────────────────────────────────┐
│  階段 2: 配貨                                                            │
│  ─────────                                                              │
│  1. 查詢待配貨的 SPOD（AGGREGATED 且對應 BPO 已收貨）                     │
│  2. 依優先度排序、FEFO 取批次分配                                         │
│  3. 產生 AO + AOD                                                        │
│  4. AOD.status = PENDING                                                │
│  5. 大庫庫存扣減（預留）                                                  │
│  6. SPOD.status = ALLOCATED（終態，防重複配貨）                           │
└─────────────────────────────────────────────────────────────────────────┘
        │
        ▼ 等待業務員領貨
┌─────────────────────────────────────────────────────────────────────────┐
│  階段 3: 領貨                                                            │
│  ─────────                                                              │
│  - 業務員確認領取                                                        │
│  - 更新 AOD.status = RECEIVED                                           │
│  - 詳見 SalesReceiveOrder.md                                            │
└─────────────────────────────────────────────────────────────────────────┘
```

## 配貨規則

### 分配演算法（2026-07-09 定案）

1. **待配貨資格**：`SPOD.status = AGGREGATED` 且對應 BPO 已收貨（RECEIVED / DISCREPANCY，貨到才配）
2. 業務員依 `priorityLevel ASC` 依序分配；批次一律依 FEFO（`expiryDate ASC, batchNo ASC`）取貨，單一批次不足時**跨批次拆分**（同一 SPOD 產生多筆 AOD）
3. 庫存不足時，低優先等級的業務員可能分配不到（allocatedQty = 0），**不自動補配**；配不足即為終態，系統**不追蹤補配流程**（補配走線下人工協調），另提供「缺配清單」查詢（`confirmedQty > Σ allocatedQty` 的 SPOD）供庫務／業務檢視缺口（2026-07-21 定案）
4. 配貨完成後 `SPOD.status → ALLOCATED`（終態；分到 0 也標，防止重複配貨）

完整演算法步驟與範例見[業務員優先度規格書](../branch/SalesPriority.md)。

### 優先度設定

優先度透過 `SalesPriority` 資料表設定，詳見[業務員優先度規格書](../branch/SalesPriority.md)。

## 資料結構

> 欄位定義（名稱、型別、nullable）以 Entity 為準，個別欄位語意見其 Javadoc：
> - 單頭：`src/main/java/com/agony/wmsallocation/entity/allocation/AllocationOrder.java`
> - 明細：`src/main/java/com/agony/wmsallocation/entity/allocation/AllocationOrderDetail.java`

結構重點（不隨欄位改名變動的部分）：

- AO 粒度為營業所 + 日期，同一天可多張（多次配貨）
- AOD 記錄目標儲位、產品、批次、效期、**預定數量**（來自 SPOD.confirmedQty）與**實際配貨數量**（庫存不足時可能為 0）
- AOD 狀態追蹤領取進度（PENDING → RECEIVED）

---

## AOD 狀態說明

| 狀態 | 說明 |
|------|------|
| PENDING | 待領取（已配貨，等待業務員領取） |
| RECEIVED | 已領取（業務員已確認領貨） |

## AO 狀態說明

| 狀態 | 說明 |
|------|------|
| PENDING | 尚有明細待領取 |
| RECEIVED | 全部明細皆已領取（**狀態約束**：此為聚合狀態，為了查詢效能而落地；最後一筆 AOD 轉 RECEIVED 時同步轉態。2026-07-21 定案） |

## 單據關係

```
SPOD (業務員訂貨明細)
    │
    ▼ 庫務配貨
AO ─┬─ AOD (產品A, 批次B1, 給業務員S1)
    ├─ AOD (產品A, 批次B2, 給業務員S2)
    └─ AOD (產品B, 批次B3, 給業務員S1)
    │
    ▼ 業務員領貨
SRO (業務員 S1 領貨單)
├── SROD ← AOD (產品A, 批次B1)
└── SROD ← AOD (產品B, 批次B3)
```

## API 設計

> 端點定義（路徑、HTTP method、請求/回應格式）以 Controller 為準，或由 Swagger/OpenAPI 自動產生。

對外提供的能力（操作者：庫務）：

- 查詢配貨單清單
- 查詢單一配貨單明細
- 執行配貨
- 查詢待配貨的 SPOD
- 查詢缺配清單（`confirmedQty > 實配量` 的 SPOD，供線下補配協調；2026-07-21 定案）
