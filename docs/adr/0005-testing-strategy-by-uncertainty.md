# 5. 測試策略：依不確定性選 test-first／test-after，測在邏輯所在層

日期：2026-07-01

## 狀態

已接受 (Accepted)

## 背景

本專案是學習專案，開發者原本期望全程走 TDD（test-first：先寫測試 → 看紅 → 再實作），但實作到主檔 CRUD 時感到明顯的摩擦，來源有二：

1. **迴圈時間**：現有測試分四層，成本天差地別。Service 測試是純 Mockito（毫秒級），但 Controller（`@WebMvcTest`）、Mapper（Spring context）、Repository（`@DataJpaTest` + Testcontainers 拉 SQL Server 容器，十幾秒且需 Docker）都帶開機稅。TDD 的紅→綠 迴圈一旦滲入這些層的開機時間就變得很痛。
2. **ceremony（形式成本）**：對已經寫過數次、形狀爛熟的機械功能（第 N 個一模一樣的 CRUD），先寫測試看紅並沒有給出任何新資訊，只是把實作用測試語法先抄一遍。

早期的先例也不一致：Branch 四層全寫測試（且它 repo 層有一支自訂 `@Query` 值得測），SalesOrganization 卻零測試。代表當時並無成文規則，每次即興判斷。

核心觀察：**TDD 的「看紅」這步，價值在於「當你還不確定程式該長怎樣、邊界該怎麼行為時，逼你先想清楚」——它是設計工具。** 對設計早已定死的機械功能，這個價值不存在；對業務邏輯尚未定案的功能，這個價值最大。「有測試（回歸網）」與「test-first（工作流）」是兩件可分開的事：可以保留前者、按情況丟掉後者。

## 決策

我們將**依「不確定性」而非「層」或「功能種類一律套」來決定測試工作流**：

- **機械、已知形狀的功能（主檔 CRUD 等）**：採 **test-after**——先寫實作，再補測試作回歸網，跳過無意義的看紅。
- **有真實邏輯、設計尚未定案的功能（allocation／inventory／sequence／purchase 等業務規則）**：採 **test-first 走 TDD**——把 TDD 的力氣留在這裡，看紅在此才真正幫助釐清行為、也才學得到東西。

並且**測在「你的邏輯所在的那一層」，不反射性地每層都測**：

- **Service 層**：業務分支（重複／找不到／下轄檢查／軟刪 vs 硬刪／預設狀態／身份不可改）集中於此，且純 Mockito 迴圈最快——**這是主要的測試投資點**。
- **Controller 層**：多為機械分派。想釘 `@Valid` 是否掛上與 status code（201/200/204）契約時，每個主檔挑一次代表性的寫即可，不必逐端點重測。「例外→HTTP status→ErrorResponse」的泛用對映已由 `GlobalExceptionHandlerTest` 集中釘死，不重複。
- **Repository 層**：僅在出現自訂 `@Query` 或不直觀的衍生查詢時才寫（純衍生查詢由 Spring Data 保證，測它等於測框架）。此類測試需 Testcontainers，成本最高，應保持稀少。
- **Mapper 層**：僅在出現非平凡 `@Mapping`（改名、型別轉換、ignore）時才寫（直接搬運由 MapStruct 保證）。

## 後果

- 兩種摩擦同時解除：TDD 迴圈只碰毫秒級的 Service Mockito 測試（迴圈時間）；簡單功能不再被逼著先寫紅（ceremony）。
- 回歸網仍在：機械功能改走 test-after 而非「不測」，Service 層的行為仍被釘住。
- Branch 既有的四層測試不需回頭刪除——它是「第一個做完整當範本」，且 repo 層那支自訂 `@Query` 本就符合本策略的 repo 測試門檻，予以保留。
- 新的判斷成本：「這功能算不算已知形狀 / 有沒有非生成的邏輯」需要開發者自行判斷；本 ADR 提供原則而非機械規則，邊界情況靠 code review 收斂。
- **這是學習專案的取捨**：TDD 作為一種要練的實踐仍有價值，但練在「需要想清楚」的業務邏輯上才學得到；在一模一樣的 CRUD 上硬練只會累積對這個實踐的反感。
