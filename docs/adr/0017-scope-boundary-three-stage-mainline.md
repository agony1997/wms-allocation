# 0017. 範疇界定為訂貨 → 配貨 → 領貨出庫三段主線

日期：2026-08-12

## 狀態

已接受 (Accepted)

## 背景

本專案的程式碼與規格承襲自前身專案，該專案定位為模擬完整的經銷體系（訂貨 → 收貨 → 配貨 → 送貨 → 結帳），五段全做。實際進度是：前三段（訂貨、收貨、配貨）已有完整的 Service／Controller／測試，後兩段（送貨 delivery、結帳 closing）**只有 Entity，沒有任何行為**。

重新建立專案時，範疇是必須先定的事——它決定哪些 Entity 該存在、哪些規格該帶、哪些庫存異動方法有呼叫者。維持五段等於承接一塊只有骨架的區域，而它是目前最大的未完成區塊。

另一個輸入：本專案是 side project，沒有真實使用者。範疇的唯一評判標準是「這一段能不能讓專案回答出更難的問題」，而非業務完整性。

## 決策

### 一、實作範疇

| 段 | 內容 |
|----|------|
| **訂貨** | 業務員訂貨（SPO）→ 門市彙總（BPF/BPO）→ 工廠出貨（FDO）→ 收貨入庫 |
| **配貨** | 待配明細撈取 → FEFO × 優先度分配 → 建 AO/AOD ＋ 扣庫存 ＋ 明細轉態（單一交易） |
| **出庫** | 領貨單（SRO/SROD）：庫存由大庫移轉至業務員車存 |

終點是「貨到業務員車上」。系統形態由 Van Sales（車銷外務）收斂為**倉儲補貨與配貨出庫**。

### 二、為什麼停在這裡

這三段已經涵蓋本專案想證明的兩件事：

1. **演算法正確性**——FEFO × 業務員優先度 × 批次拆分，是純函式可窮舉邊界的真實邏輯；
2. **併發正確性**——多業務員同時配貨、庫存不得超賣，靠資料庫悲觀鎖與單一交易邊界保證（[ADR-0013](0013-inventory-pessimistic-lock.md)）。

送貨與結帳會讓系統更完整，但它們是另一組 CRUD 與狀態機——**增加的是體積，不是這個專案回答不了的問題**。在可用工時稀缺的前提下，體積是負債。

### 三、暫緩而非放棄

送貨與結帳標記為**暫緩**，處置如下：

| 項目 | 處置 | 理由 |
|------|------|------|
| `docs/requirements/specification/delivery/`、`closing/` | **保留** | 已想過的設計，文件不編譯、零執行成本 |
| `entity/delivery/`、`entity/closing/`（17 檔） | **不建立** | 會被 `ddl-auto` 建表、被 IDE 索引，讓人誤判為待辦。照規格重建約 1 小時 |
| `InventoryService` 的 `sell`／`customerReturn`／`keep`／`keepRetrieve`／`returnGoods`／`returnShip` | **保留** | 有 22 例測試護著；砍掉要加回來就是重寫加重測 |
| SROD 的 `sourceType`（寄庫作為第二來源） | **現在不加** | 為想像中的需求付款；實作寄庫時再放寬 schema |

**這批沒有呼叫者的方法與規格不是待辦訊號**，已寫入 `AGENTS.md` 的範疇界線與「不要修的清單」——否則後續的 AI session 會把它們當成死程式碼「清理」，或當成未完成功能去實作。

## 後果

- **正面**：範疇與實際完成度對齊，不再有一塊只有 Entity 的空白區；刪掉 17 個無行為的 Entity 後，`ddl-auto` 建的表與實際業務一致；剩餘的後端業務工作收斂為單一項目（SRO 領貨）。
- **負面／承擔**：
  - demo 講不到「賣給客戶」與「收帳」，故事在「貨上車」處結束。
  - 若日後決定加回，需重建 Entity 並補 SROD 的 `sourceType`——約 1 人天的重工，這是刻意接受的代價（換取現在不維護空骨架）。
  - 系統名稱與定位需隨之改變（不再是 Van Sales 車銷系統，而是倉儲配貨系統），對外說明要一致。
- **被否決的替代方案**：
  - **維持五段全做**：後兩段是最大的未完成區塊，且不增加專案能回答的問題深度。
  - **連 delivery/closing 規格一起丟棄**：規格是已付出的思考成本，保留不佔執行成本，丟掉才是浪費。
  - **保留 Entity 但不實作**：看似兩全，實際會讓 `ddl-auto` 建出無人使用的表，且每個新 session 都要重新判斷「這些要不要做」。
