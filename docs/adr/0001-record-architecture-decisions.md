# 1. 採用 ADR 記錄架構決策

日期：2026-06-29

## 狀態

已接受 (Accepted)

## 背景

本專案是以手動開發為主、AI 輔助為輔的學習專案。隨著開發推進，許多架構決策（為何用三層架構、為何 API 不包統一信封、為何 `ddl-auto=create`）原本散落在 `AGENTS.md` 與口頭討論中，存在兩個問題：

- **背景流失**：只記錄「現在怎麼做」，沒記錄「當初為什麼這樣選、否決了什麼」，未來回看或重新評估時得重新推導。
- **AI 協作脈絡**：AI agent 在輔助時需要理解決策背景才能給出一致的建議，但常駐指引檔（AGENTS.md）不適合塞滿冗長的決策論述。

對學習專案而言，「想清楚並寫下為什麼這樣決定」本身就是核心價值。

## 決策

我們將採用 **Architecture Decision Records (ADR)** 記錄架構決策，放在 `docs/adr/`：

- 採用 **Michael Nygard 格式**（背景 / 決策 / 後果），精簡且廣泛通用
- 純 markdown、零工具依賴，檔名 `NNNN-kebab-title.md`，流水號手動遞增
- ADR 只增不改；決策被推翻時新增一篇並將舊篇標記為「已取代」
- ADR 記錄**為什麼**；操作層面的**怎麼做**留在 `docs/conventions/`，兩者互相連結

## 後果

- 決策背景有了單一、可版控、可追溯的記錄，降低未來重新評估的成本。
- `AGENTS.md` 得以瘦身為索引，把決策論述移到 ADR，常駐 context 更輕。
- 需要一點紀律：做出重要架構決策時要記得補一篇 ADR，否則目錄會與實際脫節。
- 不引入 `adr-tools` 等 CLI（在 Windows/PowerShell 環境不順手，自動化效益對本專案規模不大），代價是流水號與索引需手動維護。
